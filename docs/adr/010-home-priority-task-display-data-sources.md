# 首页优先任务展示数据来源：数值走任务快照、物品名走读时查询端口

首页「优先处理任务」此前每行渲染写死的标题（`"临期任务"`/`"低库存任务"`/`"优先任务"`），没有具体内容。本次改为每行展示具体信息：临期任务显示「××还有 N 天到期」，低库存任务显示「××仅剩 N，低于阈值 M」。

关键分歧是这些展示字段的**一致性来源**：物品名是实时查，还是随任务快照一并落库？数值是否也要实时读？

决定：

- **物品名读时实时取**：任务表只存 `item_id`，不存 `item_name`。dashboard 组装首页数据时，通过新增的 `CatalogApi.itemNames`（返回 `Map<UUID, String>`）一次性补齐名字。改名即时可见，无滞后、无事件同步。
- **数值走任务快照**：剩余数量取任务的 `qty_snapshot`，阈值取 `threshold_snapshot`。快照虽在 reconcile 时刻钉死，但每次库存变更事件（全部流水路径，含冲正、盘点调整）都会触发重算，库存未变即快照仍然成立，故等价于实时。
- **物品名不进任务快照**：任务快照的定义在 CONTEXT.md 中明确排除物品名——名字是活数据，快照存历史不存展示字段。
- **改提醒规则触发全量重算**：封堵「库存未变但阈值变了」的滞后窗口。`updateRule` 写入成功且审计成功后，发布内部事件 `ReminderRuleChangedEvent`，由 `@TransactionalEventListener(AFTER_COMMIT)` 监听器在事务提交后用 REQUIRES_NEW 事务对全部活跃物品全量重算（复用当日扫描的 `reconcileAllForHousehold`，但不刷新 snoozed 到期）。重算失败只记日志、不破坏已提交的规则，每日 03:00 全量扫描兜底。窗口收窄后批次落出提醒窗口（`severity == null`）时，reconcile 同步关闭既有 OPEN 临期任务（原因 `OUT_OF_WINDOW`），避免残留过期任务。
- **临期标题的过期文案**：`daysLeft < 0` 显示「已过期 N 天」、`== 0` 显示「今天到期」，避免首页出现负数天数。

权衡与拒绝项：

- 拒绝「物品名快照进任务表」：改名后首页显示旧名直到每日 03:00 扫描，家庭成员会感觉系统不准。reporting 投影接受名字滞后是因为那是历史流水读模型，而首页是当前状态视图。
- 拒绝「物品名快照 + ItemChangedEvent 监听同步」：`ItemChangedEvent.changeType=UPDATED` 是粗粒度（改备注/封面/标签也触发），要区分「真改名」需扩事件契约或加字段；而读时查询一次即可做到即时一致的零成本等价物。为展示一个名字引入跨模块事件消费与去重机制，得不偿失。
- 拒绝「首页数值读时实时聚合」：会与「任务」本体语义冲突——任务表就是将状态钉在 reconcile 时刻的快照实体，实时聚合视图不是任务。若数值也实时，首页就不该读任务表，而应实时重算风险视图，等于废弃既有任务模型。
- 不采用 8 次 `requireItem` 逐条拼装：`itemNames` 批量端口一次建对，避免 reminder 后续展示（任务详情、邮件预览）各自拼查。归档物品在 `itemNames` 中缺失时，由调用侧以 `itemId` 兜底显示。
