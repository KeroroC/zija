# ADR-014: 库存并发控制与幂等设计

## 状态

已批准

## 背景

知家的库存写入必须防并发超支、防重复扣减、防负库存。spec §11.2 要求库存写入在事务中锁定受影响库存位，幂等标识防止重复流水。如何在单体 + 单 PostgreSQL 实例下保证正确性？

## 决策

### 1. 事务边界

每个库存命令在**单个数据库事务**内完成：流水写入、库存位更新、幂等记录、审计和公开事件登记原子提交。事务失败则全部回滚，不留下半成品。

### 2. 锁顺序

- 先按 UUID 固定顺序锁定相关批次（`SELECT ... FOR UPDATE`）。
- 再用显式 `SELECT ... FOR UPDATE` 锁定库存位。
- 固定 UUID 排序消除死锁的可能性（所有事务以相同顺序获取锁）。
- **不依赖 MyBatis-Plus 的 `OptimisticLockerInnerInterceptor`** 处理库存位数量扣减。乐观锁适用于元数据编辑（物品、位置、提醒规则），不适用于库存并发扣减。
- 库存位的 `revision` 字段用于盘点快照比对，不作为并发扣减依据。

### 3. 原子扣减

扣减使用条件 UPDATE：`UPDATE stock_position SET quantity = quantity - ? WHERE lot_id = ? AND location_id = ? AND quantity >= ?`。返回 0 行即库存不足，映射为业务错误。这与 DB 层 `CHECK (quantity >= 0)` 构成双重防护（见 ADR-013）。

### 4. 幂等设计

- 每个写入接口接受 `Idempotency-Key`（通过 `X-Idempotency-Key` 请求头）。
- **同一幂等键 + 相同请求体**：返回首次操作结果，不产生新流水。
- **同一幂等键 + 不同请求体**：返回 `409 INVENTORY_IDEMPOTENCY_CONFLICT`。
- **失败回滚**：不留下成功幂等记录，客户端可用同一键重试。
- 幂等记录与流水在同一事务内提交。
- 网络重试复用同一幂等键；业务内容改变后生成新键。客户端无需感知服务端状态。

### 5. 盘点快照

- 草稿创建时记录范围内所有库存位的 `revision`。
- 确认时比较整个范围的库存位集合与快照 revision：任一库存位在草稿期间发生变化则确认失败。
- 盘点差异条目原因必填；可补录已有批次且账面为零的条目；全新批次先走入库再刷新盘点。

### 6. 移位加锁

- 移位两端按 `(lot_id, from_location_id, to_location_id)` 的 UUID 排序统一加锁，先扣来源再加目标。
- 来源与目标不能相同，在同一事务内完成。

### 7. 事件发布

- `StockChangedEvent` 在命令事务内通过 Spring Modulith 事件登记（事务内入 `event_publication` 登记表），事务提交后由可靠投递器异步发布。
- 投递失败由 Spring Modulith 的 `event_publication` 登记机制重试，不阻塞库存业务返回。
- 事件携带唯一 `eventId`，消费者可据此去重。

## 考虑过的备选

- **乐观锁（version + CAS）扣减库存**：并发冲突时需重试，重试次数不可控；且扣减与流水写入不在同一原子操作中。`FOR UPDATE` 行锁在单库场景下更直接可靠。
- **应用层校验数量后直接 UPDATE**：校验和扣减之间有 TOCTOU 窗口，并发下可超支。原子 `WHERE quantity >= ?` 是不可绕过的。
- **幂等仅靠去重表查询**：查询和插入不在同一事务内也有 TOCTOU 窗口。幂等记录与流水在同一事务内提交才安全。
- **Kafka/Rabbit 消息中间件**：spec §3.3 明确不做。Spring Modulith 事务内事件登记 + 本地重试在单家庭规模下足够。

## 后果

- 并发消费者无法超支同一库存位、无法重复扣减、无法造成负库存。
- 幂等标识覆盖网络重试和重复点击，客户端无需感知服务端状态。
- 代价是 `FOR UPDATE` 行锁在高并发下可能成为瓶颈，但单家庭规模（20 成员）完全可接受。
- 事件投递失败不影响库存写入成功，但需 dead-letter + 重试机制兜底（见 ADR-016）。
