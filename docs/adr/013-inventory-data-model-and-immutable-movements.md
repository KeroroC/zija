# ADR-013: 库存数据模型与不可变流水

## 状态

已批准

## 背景

知家的核心价值是"知道还剩多少库存"和"知道哪些批次即将过期"。spec §5.3 要求当前库存可由流水重建，任何操作不得造成负库存。如何设计数据模型使得库存正确性可以被验证和审计？

## 决策

### 1. 四层领域模型

```
Item（物品）→ Lot（批次）→ StockPosition（库存位）→ Movement（流水）
```

- **Item**：描述"是什么"，归属一个家庭，引用后只归档不硬删除。
- **Lot**：描述"某次购入或某件独立资产"，到期日、批次号、序列号均可选但至少关联物品。批次归属物品创建后不可修改；批次日期、编号、序列号、备注可通过版本号修正并审计。
- **StockPosition**：描述"某批次在某位置的当前数量"，`(lot_id, location_id)` 唯一，是持久化的投影。
- **Movement**：描述"一次不可变的数量变更记录"，是库存事实来源。

### 2. 不可变流水

- 流水类型：`INBOUND`（入库）、`CONSUME`（领用）、`LOSS`（报损）、`ADJUSTMENT`（盘点调整）、`TRANSFER`（移位）、`REVERSAL`（冲正）。
- **流水表只有 INSERT 路径，无 UPDATE、无 DELETE**，不使用数据库触发器。
- 库存位是持久化投影，流水是事实来源。当前库存位数量 = 该位置该批次所有有效流水的代数和。

### 3. 冲正机制

- 冲正只创建等量反向 `REVERSAL` 流水并引用原流水（`reversal_of`），保留原始记录，不修改也不删除原始流水。
- 不允许对已冲正的流水再次冲正。
- 不允许执行会导致负库存的冲正。

### 4. 一致性检查

- 遍历指定范围库存位，按流水汇总重算应有数量与库存位实际数量比对。
- **只读不写**：发现差异只报告，由人工决定后续冲正或盘点，不自动篡改流水或库存位。

### 5. 负库存防护（双重兜底）

- **应用层**：扣减使用原子 `UPDATE ... SET quantity = quantity - ? WHERE quantity >= ?`，返回 0 行即视为库存不足。
- **数据库层**：`stock_position` 表 `CHECK (quantity >= 0)` 约束作为最终兜底。
- 任何操作路径都无法绕过这两层防护。

### 6. 转移流水

- 移位由一条 `TRANSFER` 流水表达，但在同一事务内同时更新来源和目标两个库存位。
- 来源与目标不能相同；移位两端按 `(lot_id, from_location_id, to_location_id)` 的 UUID 排序统一加锁。

### 7. 耐用品与消耗品统一模型

- 物品有 `CONSUMABLE` 和 `DURABLE` 两种管理类型，但共用批次、位置和流水模型。
- 同一批次可分散在多个位置，因此位置不能只存在批次记录上。
- 物品只有一个基础计量单位，首期不自动换算。

## 考虑过的备选

- **流水可编辑**：破坏可审计性，无法回答"这个数量为什么变了"。不可变 + 冲正是标准实践。
- **库存位 = 实时聚合流水**：每次查询都重算 100 万条流水，性能不可接受。库存位作为持久化投影 + 定期一致性检查是平衡点。
- **负库存仅靠应用层校验**：并发场景下应用层校验和扣减之间有 TOCTOU 窗口，DB CHECK 是不可绕过的最终防线。
- **物理删除归档物品**：已关联的流水和历史展示失去可解释性。归档保留历史链路。

## 后果

- 任何库存位数量都可由有效流水重建和验证，满足"数据正确优先"设计原则。
- 冲正保留原始记录，审计链完整。
- 一致性检查只报告不自动修复，避免机器决策篡改事实。
- 代价是流水表持续增长，未来需要归档策略（首期不实现自动清理）。
